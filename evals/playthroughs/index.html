Watching a model play

Intra is a text adventure. A language model operates the game. In the recordings below, a different model plays the game. The player model has a quest to complete and a limit on its turns. Nobody helps it.

We made these recordings to answer a development question: can a model play this game, and where does play stop? We publish the failed runs together with the good runs, because the failed runs show more.

Warning: these transcripts can show the solutions to the mysteries of the game. If you want to find the solutions in play, play the game first.

How a quest run works

Two models operate in each run. The game model plays all the characters, describes the rooms, and sends the tags that the engine obeys. This is the same configuration as normal play.

The player model plays the player. It can see only the data that a human player can see: the transcript, the current room, the exits, the persons in the room, the task list, and the names of the open mysteries. It cannot see the mystery hints. It cannot see the character instructions. The code in evals/playerview.ts makes this view. A test makes sure that the mystery answers are not in the view.

The player model keeps notes between its turns. The notes are its memory. It writes the notes for itself. The pages below show the notes without changes. The notes show what the player model believed, and what it planned, before each turn.

The engine measures progress. It does not ask a model for an opinion. A milestone, for example met-marta, is a check of the world state after each turn. A mystery counts as solved only when the game fires its own <resolveMystery> instruction.

The pages show these counts also. Repeats is the number of turns where the player went to the same room again, or asked the same question again. Fumbles is the number of commands that the game could not use. Snags are moments where the game gave incorrect information to the player. A snag is a defect in the game, not in the player.
