1.4░▒▓ Where it came from

The original thesis

There's lots of LLM-based games that let the LLM hallucinate the entire story. But these have a dreamlike quality to them... things come into existance only as they are imagined. They are ungrounded. A normal text adventure has a very strict structure, with a set of formal commands to navigate that structure. In this game I'm trying to have a bit of both. There's an underlying game model and a grounding to the story, but with opportunities for the user and LLM to navigate that together in imaginative ways.README.md, FAQ
I want ground truth because there's a kind of hedonistic nihilism to a game driven by narrative necessity. [...] I want the formal code to know if you are holding the key or you are not holding the key.ianbicking.org, 2025
notesTypo "existance" is in the shipped README.

The tension in one line: if the model can improvise, it can improvise things that are not true. Known Problems item 1 is the same statement.

Decision one: tags, not tool calls

I deliberately did not use Tools or function calls for this. The basic model of how a tool works isn't good for a game. [...] I really want the LLM to simply state what should happen, and then make it happen, and not return to the LLM at all.README.md, FAQ
when getting an LLM to simulate some fictional entity it's very useful to present the task as something like dialog generation, and never make the LLM "pretend" to be another person. Instead the LLM plays the part of a script writer.README.md, FAQ

Tool-call version, for comparison: a turn is one pass in which the character speaks, moves, sets state and updates the task list at once. As a tool call that is one large, flexible call per turn, and a loop the small target models handle badly.

1.6░▒▓ Where it came from

Decision two: the event log is the game

The event log is the game. The world — where everyone is, what Ama knows, what's on your task list — is computed by replaying the log, and is never stored on its own. A save is a log. A checkpoint is a log, so starting the game partway through is just replaying one. A server session is a log in Durable Object storage. An eval replays a log and checks what state it produced.docs/agent-install.md

The general name is event sourcing. Nothing is snapshotted: the whole world is rebuilt from the log every time it is needed.

SAVE, SERVER, CHECKPOINT, EVAL: four labels accepted; one box issued.

notesConsumers of the same log: saves, checkpoints, evals, the quest runner, undo, the server's Durable Object.

Known Problems entry: "event serialization is load-bearing". The log is the save format, the checkpoint format and the eval input, so its shape is hard to change.

2.3░▒▓ The engine

Undo is an append

The update stream is the game's source of truth *and* — once sessions live on a server — its audit trail. So undo must not delete anything: instead it appends an event carrying a rewind count, and the events it supersedes are filtered out when the world is folded. That keeps the log append-only (a reviewer can still see what the model produced and that the player took it back), while the game behaves as if those turns never happened.lib/game/rewind.ts
the entire implementation
export function applyRewinds(updates: StoryEventType[]): StoryEventType[] {
  const live: StoryEventType[] = [];
  for (const update of updates) {
    if (update.rewind) {
      live.length = Math.max(0, live.length - update.rewind);
      continue;
    }
    live.push(update);
  }
  return live;
}

  • Conventions: a line starting with > is an action, with " is dialogue

2.8░▒▓ The engine

An action is resolved by a second prompt

the two prompts, with the examples the prompts themselves use
player input    open the door
                →  <action minutes="10">Pat attempts to open the door.</action>

player action   d20 = 14
                →  <actionResolution success="true" minutes="5">The door opens.</actionResolution>
  • The adjudicator gets the room and its description, who is present, the room's own action notes, any sealed exits, the last four history entries, and a d20
  • Trivial actions always succeed. A 1 is a critical failure, a 20 a critical success. It may use the roll or decide by plot
  • It resolves only what the attempt physically does. People in the room respond on their own turn
  • It may not invent objects or information that answer a mystery
  • A room can carry action notes: the Foyer's say a locked door "unlocks" if the player tries, and add <removeRestriction>. A sealed exit fails whatever the roll
notesPrompt: assembleActionPrompt in lib/game/classes.ts. Genre line in the prompt: "absurd and comedic sci-fi, in the style of Hitchhiker's Guide to the Galaxy or the movie Brazil."

Seven context questions before the tag: possible at all; trivial; outcome on success; outcome on failure; difficulty from VERY EASY to VERY HARD; use the roll or decide by plot; any tags the room notes call for.

The roll comes from Math.random, which the evals and cassettes replace with a seeded generator, so a scenario rolls the same number every run. The result is stored on the event as an actionAttempt with success, minutes, the resolution text and the roll.

2.10░▒▓ The engine

Two severities, and the line between them

What goes in is limited to mistakes a model could plausibly fix if told — a misspelt attribute, a value of the wrong shape — because the point is to hand it back and ask again. Anything the model cannot act on is a warning and stays one.lib/game/tags.ts, on the complaints channel

Complaint → one retry

  • <attitude toward=> naming nobody
  • <set> on an attribute that does not exist
  • <set> with an unusable value

Warning → skip and move on

  • An unknown tag
  • <resolveMystery> with a bad id
  • <todoDone> matching no open task

RETRY drawer: 12 / INCIDENT drawer: 2 / drawer handles color-coded after incident 2

notesBefore any of this the parser repairs what it can: auto-closes unclosed tags, recovers mismatched closing tags, strips <b> <i> <em> and backticks, hoists a <set> written inside a <dialog>, keeps loose text. 2024 commit: "Some models produce these regularly, and I'm going out of my way to avoid them through instructions which is distracting."

Normalisation on input: "he", "he/him/his" and "He / Him" become he/him; several spellings of true and false are accepted; a profession of "unknown" is refused.

Most common protocol failure across every model measured: <set> on an attribute that does not exist. Examples seen: PLAYER.intakeStep, Ama.askingProfession. The change is applied and a warning is raised, because some flows legitimately add attributes.
